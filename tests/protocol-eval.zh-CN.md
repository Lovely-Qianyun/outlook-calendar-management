# 输出协议评估集

用于验证 agent 与脚本能否从命令输出中**稳定、无误地**提取关键信息。每次修改输出格式前后各运行一遍，以防协议被破坏。

自动化的部分位于 `tests/test_protocol.py`（同一套正则逐条固化）；本文件是供人/agent 对照使用的评估集，用于全新会话中的端到端验证。

## 提取正则（协议承诺，不得变）

| 信息 | 正则 | 说明 |
|------|------|------|
| list 的 🆔 | `^    🆔 (.+)$` | 4 空格缩进 |
| add 的 🆔 | `^   🆔 (.+)$` | 3 空格缩进 |
| read 的 🆔 | `^🆔 (.+)$` | 顶格 |
| 系列主事件 ID | `^🆕 .+?: (.+)$` | 锚点+冒号结构，顶格；冒号前文案随语言（zh: 系列主事件ID / en: Series master event ID） |
| free 时段 | `(\d{2}:\d{2})-(\d{2}:\d{2})` | 逐段 HH:MM-HH:MM；无时段列表 = 整天空闲或无空闲（区分依赖文案或 `--json`） |
| --json 错误 | `{"error": ..., "exit": 1}` | stdout 可 json.loads |

## 硬规则（违规即协议破坏）

1. **事件 ID 必须来自命令结果**：JSON 的 `id` / `seriesMasterId`，或下述 stdout 的 🆔 / 🆕 行；agent 严禁猜测或编造 ID
2. **stdout 里的 🆔 只能属于结果事件**：冲突警告等非交互提示（含现有日程的 🆔）一律在 stderr——从 stderr 提取 ID 是错误用法
3. 锚点（🆔/🆕/✅/⚠️…）与**结构**（缩进/冒号/括号/时段格式）与语言无关，zh/en 完全一致；`--json` 输出也与语言无关
4. **自然语言文案不属于协议**：行内文案（如"系列主事件ID / Series master event ID"、"确认? / Confirm?"）随语言自由翻译，agent 提取信息只依赖锚点与结构，不依赖具体文案
5. `--json` 模式下每次操作向 stdout 输出且只输出一个 JSON 值，人类提示全部在 stderr。`--help` 仍显示文本帮助；`--json` 未指定命令时返回结构化参数错误。参数、命令及依赖启动错误使用 `{"error": ..., "exit": 1}`；`status` 未连接时保留连接状态对象。
6. JSON 使用 ASCII 转义，确保 Unicode 日程内容和错误信息经过 Windows GBK 管道后，`json.loads` 仍能完整还原。

## 评估用例

对每条用例，在全新会话里让 agent 执行操作并提取信息，核对提取结果。

用例 9 的 `wednesday.json` 是 UTF-8 文件，内容为以下明确的 pattern 对象：

```json
{"type":"weekly","interval":1,"daysOfWeek":["wednesday"],"firstDayOfWeek":"monday"}
```

| # | 操作 | 期望提取 | 常见错误 |
|---|------|---------|----------|
| 1 | `list --from 2026-08-20 --days 7`，输出 3 条日程 | 3 个 🆔（4 空格行），与输出一一对应 | 误抓 stderr 内容；将时间误作 ID |
| 2 | `add "周会" "2026-08-20 15:00" "2026-08-20 16:00"`（与现有日程冲突） | 新日程的 🆔（3 空格行）| 抓到冲突警告里现有日程的 🆔 |
| 3 | `read <某次出现ID>` | 该次 🆔 + 🆕 行主事件 ID（锚点+冒号结构）两个值 | 将系列主 ID 误作该次 ID 执行删除 |
| 4 | `free "2026-08-21" --from 09:00 --to 18:00` | 空闲时段列表（HH:MM-HH:MM）；无时段列表 = 整天空闲或无空闲 | 在无时段列表的形态上误判为"有空闲时段" |
| 5 | `delete <ID> -y` 单次日程 | stdout 有删除成功行（🗑️ 锚点），无残留 ID | 忽略"可找回"提示行 |
| 6 | 任意操作 `--json`（文本帮助除外） | stdout 直接 json.loads 成功 | 将 stderr 提示混入解析 |
| 7 | `add "坏时间" "无效日期"` 出错 | stderr 有 ❌；stdout 为空 | 从 stdout 查找错误 |
| 8 | 英文环境（`--lang en`）跑 1-5 | 锚点与中文环境完全一致 | 按中文文案做断言 |
| 9 | 定期系列：`read` 某次 → `update <主ID> --repeat-file wednesday.json`，文件为明确的 weekly pattern | 主 ID 来自 🆕 行，而不是某次 ID | 用某次 ID 改规则（会被拒绝） |
| 10 | `next <系列ID>` | 下次出现的 🆔（4 空格行） | 将"系列已结束"提示误作正常输出 |
| 11 | 用户要求今天 14:00–15:00；先 `context --json`，再用已确定的绝对开始/结束和命名时区执行 `add` | 输出日期与本次规范化所用的上下文日期一致；后续验证/重试复用相同参数 | 将语言直接传 CLI；使用旧会话日期；跨午夜后重新解释 |
| 12 | 中英文执行 `move <单次或主事件ID> --days 1 --json`，包括模拟 PATCH 失败 | 成功时为含目标 ID 和移动后日期的一个事件对象；失败时为一个错误对象。两种情况下定期日程提示都在 stderr。 | 将提示当 JSON 解析；混淆单次与主事件 ID |
| 13 | 中英文执行 `update <ID> --json`，不提供修改字段 | 一个 `{"error": ..., "exit": 1}` 对象，退出码 1；未发送 PATCH | 将空 stdout 当作成功，或重试写入 |
| 14 | `--json read` 缺少 ID、`list --days` 值非法、未知命令或模拟依赖安装失败 | 一个错误对象，退出码 1；安装诊断仍在 stderr | 误认为只有 Graph 错误提供结构化输出 |
| 15 | 中英文执行 `read <ID> --json` 并经 GBK 管道，日程含中文/emoji 或模拟 Unicode 错误 | `json.loads` 逐字还原；ASCII 转义是正常格式 | 比较原始 JSON 文本而非解码后的值；忽略被替换成 `?` 的字符 |

期望标准为 15/15。用例 12-15 由 `test_protocol.py` 离线运行，所有网络与安装调用均已模拟。任一条失败即说明输出协议被破坏，应回退改动，或同步更新本文件与 test_protocol.py。
